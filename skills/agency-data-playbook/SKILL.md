# 데이터관리팀 플레이북

## 담당 범위

볼트 노트와 AI 대화 기록이다. 검색 품질(평가 점수, 실패 질의), 볼트 정리 상태(머리말·중복·깨진 링크·관련 노트), 대화 기록 수집 누락을 본다. 납품은 분석과 개선 제안 **문서**다. 코드를 고쳐야 하면 인프라 운영팀 요청으로 넘긴다.

## 접수 때 꼭 확인할 것

명세 5칸(목표·대상·제외 범위·완료 기준·예산)에 더해 묻는다. 요청 글에 답이 있으면 인용해 확인만 받는다.

1. 무엇을 판단하려는가: 점수가 왜 바뀌었는지, 무엇을 고치면 좋은지, 정리가 필요한지 중 하나
2. 비교 기준: 언제의 점수·사본과 비교하는가
3. 넘기면 안 되는 자료: 회사 노트·`🔐` 노트는 항상 제외(그 밖에 더 뺄 것)

## 입력 자료

- 엔진의 준비 명령이 만든 `inputs/` 파일만 근거로 쓴다(검색 평가 결과, 색인 정보). 볼트 원문을 새로 모으지 않는다.
- 회사 문항(평가 세트의 `company = true`)의 질의 문장·정답 경로는 다루지 않는다. 건수와 점수만 쓴다.

## 일의 크기 규칙

| 크기 | 기준 | 요청서 |
|---|---|---|
| 작은 일 | 질문 하나에 답하는 분석 | 1건 |
| 중간 일 | 원인 분석 + 개선 후보 비교 | 2건(분석 → 제안) |
| 큰 일 | 실험이 필요한 원인 확인 | 실험 설계 문서를 먼저 납품하고, 실험 실행은 인프라 운영팀 요청으로 |

## 문서 형식

결론(2~3줄) → 근거(숫자는 기준 시각과 함께) → 한계(확인하지 못한 것은 "미확인") → 개선 후보(장단점, 바로 할 일과 급하지 않은 일) 순서로 쓴다. 상관관계만 보고 원인으로 단정하지 않는다.

## 검수 증거

- 문서의 숫자가 `inputs/` 파일 값과 일치한다.
- 회사 문항의 내용과 노트 경로가 문서에 없다.
- 원인 주장마다 근거 파일이나 통제 실험이 연결돼 있다. 없으면 "가능성"으로 쓴다.

## 하지 않는 것

- 볼트·색인·평가 세트를 고치지 않는다(읽기만).
- `🔐` 노트와 회사 노트를 읽거나 문서에 옮기지 않는다.

## 보고 형식

결론 / 완료 기준별 증거 / 한계 / 다음 요청 후보(인프라 운영팀으로 넘길 일)
